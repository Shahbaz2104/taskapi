## Executive Summary

The codebase remains well above average for its size: zero circular imports across all 55 backend files, zero `as any`/`@ts-ignore`/non-null assertions under strict TS, a genuinely race-safe idempotency design, refresh-token theft detection, HMAC-signed webhook delivery with backoff + circuit breaker, and honest tests (no skips, no `.only`, real mongodb-memory-server integration coverage above enforced thresholds).

But this pass found **two critical issues** that the 2026-08 audit could not see:

1. **2FA is completely bypassable.** `protect()` never asserts a token `purpose`, so the short-lived `2fa_challenge` JWT returned _before_ code verification is a valid `Authorization: Bearer` access token (`src/middleware/auth.ts:30-41`). Password-reset tokens are equally replayable (the still-open FIND-002, now escalated).
2. **A mid-run Redis outage stalls every request.** The global rate limiter awaits a Redis store backed by a client with `maxRetriesPerRequest: null`, no `commandTimeout`, and ioredis' offline queue — promises that never settle, mounted before `/health`/`/ready` (`src/app.ts:72-79`, `src/config/redis.ts:11-14`).

Plus a high-severity **SSRF gap** (webhook URLs accept private/metadata addresses, redirects followed), an **`as never` auth bug** that can verify an arbitrary unverified account, **empty OpenAPI** (zero documented paths), **auth rate limiters that are always in-memory**, and a **shutdown path that never drains BullMQ workers**.

**New findings (N-001…N-041):** 2 Critical · 7 High · 27 Medium · 4 Low · 1 Info = **41**.

**Reconciliation of the 2026-08 audit:** 2 resolved (FIND-001, FIND-007) · 1 mostly resolved (FIND-006) · 2 partial (FIND-004, FIND-005) · 9 still open (FIND-002 escalated into N-001, FIND-004 widened into N-002/N-005/N-011, FIND-006 residue → N-027, FIND-010 widened → N-025, FIND-014's swagger leg escalated → N-008).

## Part 2 — New findings

Severity legend: 🔴 Critical · 🟠 High · 🟡 Medium · 🔵 Low · ⚪ Info

### 🔴 N-001 — 2FA bypass: challenge/reset JWTs are valid access tokens (Critical)

- **Evidence:** `src/middleware/auth.ts:30-41` — `jwt.verify()` + `typeof decoded.userId === "string"`; no `purpose`/`aud` assertion. `DecodedAccessToken.purpose?: undefined` is type-only, reached via `as unknown as` (`src/middleware/auth.ts:33`, `src/types/auth.ts:4-7`). Challenge token: `{ userId, purpose: "2fa_challenge" }`, 5-min TTL, same `JWT_SECRET` — `src/services/auth.service.ts:184-194`, returned to the client **before** code verification at `src/controllers/auth.controller.ts:107-114`. Reset token: `{ userId }`, 30-min TTL — `src/controllers/auth.controller.ts:214-216`.
- **Impact:** With only a password, an attacker calls `POST /auth/login`, receives `challengeToken`, and uses it as `Authorization: Bearer` — **2FA provides zero protection**. Separately, any leaked reset/verification email link doubles as a 30-minute API credential (link-preview bots, mail-scanner). `README.md:90` claims purpose-scoping that the verifier does not enforce.
- **Remediation:** In `protect()`, reject any token where `decoded.purpose !== undefined` (or require `purpose === "access"`). Tag every signer explicitly (`access` / `password_reset` / `email_verify` / `2fa_challenge`) and assert `purpose` at each verify site (`src/controllers/auth.controller.ts:180,234`, `src/services/auth.service.ts:199`). Add a regression test: challenge token → `protect()` must 401.
- **Status:** ✅ **FIXED 2026-10-16** (`a2acde7`) — strict `purpose === "access"` allow-list in `protect()`; all four signers tag explicitly; reset/verify endpoints assert their own purpose; 5 regression tests added in `tests/integration/app.test.ts`.

### 🔴 N-002 — Mid-run Redis outage stalls every request (Critical)

- **Evidence:** Limiter is on every request and registered before health endpoints — `src/app.ts:72-79` (mounts), `:87-114`. Redis store issues raw commands — `src/config/rate_limit.ts:20-35`. Shared client: `maxRetriesPerRequest: null`, no `commandTimeout` — `src/config/redis.ts:11-14`. ioredis defaults: `enableOfflineQueue: true`, retry strategy never gives up → queued commands never reject. `express-rate-limit` awaits `store.increment()` with `passOnStoreError: false` by default. Same unguarded-await pattern: stats cache `src/controllers/tasks.controller.ts:71-88`, enqueues `src/services/email.service.ts:64`, `src/services/webhooks.service.ts:77`, `src/controllers/webhooks.controller.ts:85`.
- **Impact:** If Redis is reachable at boot and goes down later, **all** traffic — including Docker healthchecks against `/ready` — hangs until Redis returns. The README's "fails soft to memory stores" (`README.md:88`) only holds for boot-time failure.
- **Remediation:** Set `commandTimeout` (e.g. 500 ms) on the shared client; enable `passOnStoreError: true` on the limiter; wrap cache get/set in try/catch with DB fallback; derive `isAvailable()` from `client.status` at read time (see N-011's supervisor).

### 🟠 N-003 — `as never` lets a token without `email` verify an arbitrary account (High)

- **Evidence:** `src/controllers/auth.controller.ts:189-198` — `payload.email` may be `undefined`, cast `{ email, emailVerified: false } as never` hides it; Mongoose strips `undefined` conditions so the filter executes as `{ emailVerified: false }` → the **first unverified user** is verified. Tokens lacking `email` include password-reset (`src/controllers/auth.controller.ts:214`) and 2FA challenge (`src/services/auth.service.ts:184-194`).
- **Impact:** Reset link → `POST /auth/verify-email` with that token → arbitrary account marked verified. Today's blast radius is limited because `emailVerified` is never enforced anywhere (write/serialize only) — it becomes Critical the moment verification gates anything.
- **Remediation:** `if (typeof email !== "string") return 400` before the query; type the filter as `{ email: string; emailVerified: false }`; prefer `purpose: "email_verify"` claims.

### 🟠 N-004 — Webhook SSRF: private/metadata targets accepted, redirects followed (High)

- **Evidence:** URL schema is `z.string().url().max(2048)` only — `src/schemas/webhooks.ts:5,11`; accepts `http://127.0.0.1`, `http://169.254.169.254/…`, `http://[::1]/`, `ftp://…`, `javascript:…`. Model imposes no scheme/host rules (`src/models/webhook.ts:12-17`). Delivery: `fetch(url, …)` with **no `redirect` option** (defaults to `follow`, up to 20 hops) — `src/jobs/webhooks.worker.ts:20-31`. Response body never read/cancelled (`:33-42`) → sockets linger.
- **Impact:** Any authenticated user can point the server at internal HTTP services (blind SSRF via success/failure + `consecutiveFailures` oracle), and a public endpoint can 302 the signed POST to an internal target.
- **Remediation:** Scheme allowlist (http/https) + DNS resolution rejecting loopback/RFC1918/link-local/ULA/metadata ranges + port allowlist, re-validated at delivery time; `redirect: "manual"` (treat 3xx as failure); `await res.body?.cancel()` in `finally`; keep the existing 5 s abort (`src/jobs/webhooks.worker.ts:8,17-18`).

### 🟠 N-005 — Auth rate limiters are always in-memory, even with healthy Redis (High)

- **Evidence:** `loginLimiter`/`registerLimiter`/`forgotLimiter`/`resetLimiter`/`refreshLimiter` are built at module-evaluation time — `src/routes/auth.routes.ts:19-52`; routers import at `src/app.ts:36`, before `initRedis()` runs in `boot()` (`src/server.ts:16`). `buildLimiter` checks `isAvailable()` once at construction (`src/config/rate_limit.ts:20`), which is `false` at import (`src/config/redis.ts:6`). The global limiter (built after init) does get Redis (`src/server.ts:19` → `src/app.ts:72`).
- **Impact:** Login/register/forgot/reset/refresh limits are per-process — limits multiply ×N replicas, contradicting `README.md:42,88`. FIND-012's brute-force story is weaker than documented.
- **Remediation:** Resolve the store lazily per request (store proxy / getter), or construct these limiters inside `createApp()` after `initRedis()`.

### 🟠 N-006 — Graceful shutdown never drains BullMQ workers or queues (High)

- **Evidence:** `src/server.ts:30-42` closes PostHog → Sentry → Redis → Mongo, **no** `worker.close()`/`queue.close()` anywhere; worker handles are module-private and unexported (`src/jobs/email.worker.ts:8,26`, `webhooks.worker.ts:57,77`, `reminders.job.ts:46,71`, `trash_cleanup.job.ts:27,58`). `closeMailQueue()` is defined but never called (`src/services/email.service.ts:77-94`). Cleanup is gated inside `server.close()`'s callback with a 10 s `exit(1)` watchdog (`src/server.ts:32-39`) — idle keep-alive connections can make the watchdog fire _before_ any cleanup runs. No `closeIdleConnections()`.
- **Impact:** SIGTERM abandons in-flight jobs (BullMQ stalled-job detection later re-runs them → possible duplicate emails), tears down Redis/Mongo under active workers, and the timeout path reports failure exit codes.
- **Remediation:** Export stop functions/registry; order = stop HTTP (`closeIdleConnections` → `server.close()`) ∥ close workers → close queues → Redis → Mongo → observability; make the watchdog configurable; wire up `closeMailQueue()`.

### 🟡 N-007 — Editor-visible task returns 404 on DELETE while PUT returns 200 (Medium)

- **Evidence:** update uses `loadTaskWithAccess({ minRole: "editor" })` (`src/controllers/tasks.controller.ts:207-226`); delete loads with `Task.findOne({_id, user: auth.userId})` and `softDeleteTasks(auth.userId, …)` filters `user` (`src/controllers/tasks.controller.ts:229-247`, `src/services/tasks.service.ts:399-403`). Bulk trash/purge: same owner-only filter (`src/services/tasks.service.ts:411-416`).
- **Context:** owner-only delete is a **documented, deliberate decision** (`README.md:250` "owner only"; `docs/PROJECT_STATUS.md:42`) — not a mis-implementation. The residual issue is response semantics: a shared editor who can see the task and gets `200` on `PUT` receives `404` on `DELETE`, so clients cannot distinguish "forbidden" from "missing", and the denial code is method-dependent.
- **Remediation:** Decide and document one policy — either route DELETE through `loadTaskWithAccess({ minRole: "owner" })` and return **403** for "visible but not permitted", or keep 404 but apply it consistently across methods. Never mix 200/404 for the same principal on the same resource.

### 🟠 N-008 — OpenAPI spec serves zero paths (High, DX)

- **Evidence:** Swagger UI mounted at `/api-docs` (`src/app.ts:85`); spec built by swagger-jsdoc scanning `./src/controllers/*.ts` (`src/config/swagger.ts:100-103`); grep for `@swagger`/`@openapi` across `src/` → **zero matches**. `servers` hardcoded to `http://localhost:3000` (`src/config/swagger.ts:12-14`).
- **Impact:** ~35 routes are undocumented; the platform's "API documentation and developer experience" requirement is unmet; `/api-docs` renders an empty shell.
- **Remediation:** Add JSDoc `@swagger` blocks to controllers, or generate from Zod via `zod-to-openapi`; point `servers` at `API_PUBLIC_URL`.

### 🟠 N-009 — Client: refresh token in `localStorage`, no CSP (High)

- **Evidence:** `client/src/lib/api.ts:33,45-51` (`taskapi.refresh` in `localStorage`), access token correctly in memory (`:23`); `client/src/lib/auth.tsx:164-181` logout/refresh race can re-persist the token after sign-out (no epoch guard); `client/next.config.ts:4-10` defines no `headers()` — no CSP. Backend has zero cookie support (`httpOnly|cookie` grep over `src/` → 0). Blast radius amplified by backend theft detection: a stolen-and-rotated token causes the legitimate client's next refresh to revoke **every** session (`src/services/auth.service.ts:102-108`).
- **Impact:** Any XSS = durable account takeover + potential full-session wipe of the victim via the theft-detection path. Tradeoff is honestly documented in code (`client/src/lib/api.ts:4-8`) but unmitigated.
- **Remediation:** HttpOnly/SameSite refresh cookie via a Next BFF/proxy route; add `default-src 'self'` CSP in `next.config.ts`; session epoch guard so logout invalidates in-flight refresh responses.

### 🟡 N-011 — Boot-time Redis failure degrades permanently (Medium)

- **Evidence:** `initRedis()` runs once (`src/server.ts:16`), on failure sets `available = false` and never retries (`src/config/redis.ts:8-34`); the `"error"` listener only logs (`:15`); `isAvailable()`/`/ready` are static afterwards (`src/app.ts:104`) and Redis state never fails readiness (`:106-108`).
- **Impact:** A blip at deploy = no rate-limit sharing, no cache, **no workers/cron for the process lifetime** (`src/jobs/*.ts` each start once: `email.worker.ts:11`, `webhooks.worker.ts:60`, `reminders.job.ts:49`, `trash_cleanup.job.ts:30`) with one boot log line.
- **Remediation:** Supervisor that re-attempts init and flips `available` on close; start workers regardless (BullMQ reconnects internally) or retry start; optionally fail `/ready` when `REDIS_URL` is set but unreachable.

### 🟡 N-012 — Inconsistent retry policy; email is single-attempt; silent drops (Medium)

- **Evidence:** webhooks: `attempts: 5` + exponential backoff (`src/services/webhooks.service.ts:87-91`) ✔; email: **no** attempts/backoff → BullMQ default single attempt (`src/services/email.service.ts:64-71`); reminders: no job attempts, worker has **no** `failed`/`error` listeners (`src/jobs/reminders.job.ts:54-67`); trash: `error` only (`src/jobs/trash_cleanup.job.ts:52-54`). Boot-time Redis down: webhook deliveries **silently dropped** (`src/services/webhooks.service.ts:55,65-66`), email falls back to inline SMTP in the request path (`src/services/email.service.ts:62-74`), crons never scheduled.
- **Impact:** One transient SMTP failure permanently loses verification/reset/reminder email; reminder failures never reach Sentry/pino.
- **Remediation:** Standard queue `defaultJobOptions` (attempts 3–5, exponential backoff, `removeOnComplete`/`removeOnFail` bounds); attach `failed` listeners on all four workers; log/report dropped deliveries; fail fast or supervised-retry when Redis is configured but down at boot.

### 🟡 N-013 — Job records retained forever on 3 of 4 queues (Medium)
